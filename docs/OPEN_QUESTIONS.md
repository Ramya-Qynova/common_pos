# OPEN_QUESTIONS.md

Per the Autonomy Charter, this is **not** a stopping point — it is a list of low-risk items a human may want to review later. All items below have already been decided (see `docs/DECISIONS.md`) and do not block progress.

- D-0001: PHP 8.2.12 used locally instead of the 8.3 minimum / 8.5 target — review when the dev machine's PHP is upgradeable without risking the unrelated `pos` project that shares it.
- D-0003: Project lives at `C:\xampp\htdocs\common_pos`, a new sibling directory to the existing `C:\xampp\htdocs\pos` — confirm this is where the operator wants it long-term (e.g. local vhost name, deployment path).
- D-0008: Tamil and Hindi platform translations are machine-drafted, flagged `needs_review` — have a native speaker check them before go-live.
- D-0009: The platform guard still uses `Auth::viaRequest` (unlike the tenant guard, fixed to avoid stale-cache reauthentication after revocation) because no platform login/revocation endpoint exists yet to exercise the same bug — apply the `AuthenticateTenant`-style fix when platform auth endpoints are built.
- D-0011: Frontend stores auth tokens in plain `localStorage` for now (Phase 1, online-only) instead of the Phase 7 encrypted-IndexedDB device-key mechanism — route through that instead once Phase 7 builds it.
- D-0015: Phase 2 built catalogue/inventory backend only, no frontend screens (PRD-xx, INV-xx from section 11) — confirm this reading of the phase boundary, or ask for the screens to be added before Phase 4.
- D-0019: Phase 3 built customers/suppliers/shifts/expenses backend only, no frontend screens (CUS-xx, FIN-xx) — same reading as D-0015; confirm or ask for them to be added.
- D-0021: discount approval gating checks the `pos.sales.discount` permission only, not `discount_rules` conditions (e.g. "cashiers may give up to 5% without approval") — no rule engine evaluator exists yet anywhere; every non-permitted discount is blocked regardless of size until that's built.
- D-0022: Payment provider adapters (manual_confirm, provider_confirm/webhooks), receipt rendering, and the frontend POS cart/outbox screen were not built this phase — only cash/credit payment methods and the sale-creation API itself.
- D-0025: No `exchange` service, export-center job execution, or notification/alert delivery — `alert_rules` remains schema-only with nothing evaluating it.
- D-0021 / D-0025 (compounding): the `discount_rules`/`approval_rules` condition evaluator still doesn't exist anywhere — every discount/approval gate built since (returns, cancellations, template updates) is permission-only, the same scope boundary as D-0021.
- D-0040 / D-0041: the frontend offline module (`frontend/src/offline/*`) is real and tested but not imported by any screen — there is still no POS cart/billing screen for it to serve. Auth tokens still live in plain `localStorage` (D-0011) even though the Web Crypto device-key primitive to encrypt them now exists.
- D-0044: sync push throughput measured at 6-14 ops/s against a 100 ops/s per-worker target — fine for a single-register-at-a-time POS but worth a human's attention before relying on this for a very high-volume multi-device rollout; the fix (queue-dispatched workers) is scoped but not built.
- D-0046: the Docker Compose stack is syntax-validated but was never run end-to-end — Docker Desktop's daemon could not start in this build environment. Run `docker compose up --build` once on a machine with a working daemon before relying on it for a real deployment.
- D-0047: a failed `php artisan sail:install` silently corrupted `backend/.env`, `backend/phpunit.xml`, and wrote a stray `backend/compose.yaml` on this Windows machine before reporting failure — all three were found and reverted, but it's worth knowing this command has that side effect here if anyone runs it again.
- The single biggest item overall: this build is backend-complete and heavily tested, but almost no POS/catalogue/inventory/customer frontend UI exists (every phase since Phase 2 drew the same backend-first boundary - D-0015/D-0019/D-0022/D-0025/D-0032/D-0040/D-0041). See `docs/reports/FINAL.md` section "What is partial" for the full accounting.
